= Module 4: Validate and Operate Secure Agent Workspace
:navtitle: Validate and Operate SAW

This is the required entry point for SAW exercises. Use it after completing the
optional installation module or against a facilitator-provisioned environment.
You will configure OIDC access, validate the deployed resources, inspect failure
signals, and run OpenClaw through the SAW-managed NemoClaw sandbox.

*Estimated time:* 35 minutes

== Reference architecture mapping

This deployment realizes the reference architectures together, and each workshop
exercise maps onto one of their components:

[cols="1,2,3",options="header"]
|===
| Reference architecture | What it owns | Deployed as

| NVIDIA OpenShell
| The gateway, sandbox supervisor, and policy engine that create, govern, and
  observe sandboxes
| The OpenShell gateway inside the workspace VM, the supervisor in every
  sandbox, and the OpenShell policy applied to each sandbox

| NVIDIA NemoClaw
| The agent runtime and packaging model: OpenClaw lifecycle, onboarding,
  provider wiring, and the policy model
| The BOM-configured NemoClaw runtime inside the VM; the setup Job provisions
  OpenClaw sandboxes through the OpenShell gateway at deploy time

| OpenClaw
| The agent process, tools, workspace, and Control UI
| Runs inside the sandbox; the NemoClaw runtime drives its lifecycle, and this
  workshop reaches it through `openclaw tui`

| Secure Agent Workspace
| VM isolation, identity, secrets, and validated-pattern deployment
| The KubeVirt workspace VM, Keycloak OIDC, Vault and External Secrets, and the
  GitOps-managed configuration
|===

The standalone `nemoclaw onboard` workflow is not used because the runtime's
lifecycle job is performed at deploy time: the BOM configures the NemoClaw
runtime in the VM, and its setup Job onboards OpenClaw and wires the inference
provider through the OpenShell gateway. Module 1 showed OpenClaw running on the
raw OpenShell pod boundary; this module shows the same agent inside the
production-shaped VM boundary with the runtime, OIDC, and secrets around it.

== Entry requirements

The facilitator must provide these items for a pre-provisioned environment:

* the SAW checkout at `$HOME/git/{saw_repo_dir}`;
* an OIDC account that owns the assigned workspace;
* read access to `{saw_namespace}` and `{saw_gitops_namespace}`;
* the generated SSH key required by the native configuration target; and
* a completed setup Job and running VM.

The SAW BOM and setup Job configure the agent image, inference routing,
Vault-backed credentials, policy profiles, and sandbox lifecycle. Run all
commands from `$HOME/git/{saw_repo_dir}`.

== Learning objectives

* Configure and authenticate the SAW gateway entry.
* Verify the VM, setup Job, BOM workspaces, and gateway version.
* Diagnose an incomplete workspace from Argo CD, Job, VM, and gateway evidence.
* Run OpenClaw through the SAW NemoClaw path and identify the credential boundary.

The SAW gateway runs inside the workspace VM and uses a TLS Route and Keycloak
OIDC. Configure the local CLI with the native SAW targets:

The `make login` step opens the workshop Keycloak `openshell` realm in your
browser, not your OpenShift login. The realm is seeded with test users; use
`developer` / `developer` for the standard user path or `admin` / `admin`
when a step requires the admin role. Self-registration is also enabled on

openshell-saw-configure-gateway` caches that token for the CLI.

== Exercise 2: Validate the deployed workspace

Confirm the infrastructure state before entering the agent sandbox:

[source,bash,role="execute",subs="attributes+"]
----
cd "$HOME/git/{saw_repo_dir}"
test "$(oc -n {saw_namespace} get job/{saw_gateway_name}-setup \
  -o jsonpath='{.status.conditions[?(@.type=="Complete")].status}')" = "True"
test "$(oc -n {saw_namespace} get vmi/{saw_gateway_name} \
  -o jsonpath='{.status.phase}')" = "Running"
oc -n {saw_gitops_namespace} get applications.argoproj.io
----

== Exercise 3: Diagnose an incomplete deployment

If validation fails, inspect each reconciliation layer before rerunning setup:

[source,bash,role="execute",subs="attributes+"]
----
oc -n {saw_gitops_namespace} get applications.argoproj.io
oc -n {saw_namespace} get job/{saw_gateway_name}-setup \
  vm/{saw_gateway_name} vmi/{saw_gateway_name}
oc -n {saw_namespace} logs job/{saw_gateway_name}-setup --tail=80
openshell --gateway {saw_gateway_name} sandbox list --workspace {saw_workspace}
----

Use the first failing layer as the recovery boundary. Do not delete the setup
Job until the owning Argo CD application is healthy and you know how it will be
recreated. If the token alone has expired, run
`openshell gateway login {saw_gateway_name}` instead of reconfiguring the VM.

== Exercise 4: Launch OpenClaw in the NemoClaw sandbox

The SAW setup Job provisions the `nemoclaw` sandbox from the configured BOM. Use
the Makefile target to connect to it:

[source,bash,role="execute",subs="attributes+"]
----
OPENSHELL_SAW_NAME={saw_gateway_name} \
  SANDBOX_NAME={saw_sandbox} \
  WORKSPACE={saw_workspace} \
  make openclaw-tui
----

The target uses `openshell sandbox exec` to start `openclaw tui` in the selected
workspace. The agent reaches the virtual `inference.local` route; the
gateway-side provider holds the upstream endpoint and credential. The
standalone `nemoclaw onboard` workflow is not used.

Confirm the sandbox and its policy from a second terminal:

[source,bash,role="execute",subs="attributes+"]
----
cd "$HOME/git/{saw_repo_dir}"
openshell gateway select {saw_gateway_name}
openshell sandbox list --workspace {saw_workspace}
openshell policy get {saw_sandbox} --workspace {saw_workspace} --full
----

The sandbox is managed by OpenShell and provisioned by SAW. Do not create a
second sandbox with `nemoclaw onboard` or point the standalone NemoClaw CLI at
the harness gateway.

== Exercise 5: Run and verify an agent request

Use the TUI to ask the agent to write a file in its permitted workspace:

[source,text]
----
Write a short haiku about Kubernetes to /sandbox/haiku.txt, then read it back.
----

After the file is created, exit the TUI or use a second terminal to verify it:

[source,bash,role="execute",subs="attributes+"]
----
openshell --gateway {saw_gateway_name} sandbox exec \
  -n {saw_sandbox} --workspace {saw_workspace} -- \
  test -s /sandbox/haiku.txt
----

The reason for using the SAW-managed path is lifecycle control. If the agent
image, route, policy, or access state changes independently, the operator loses
a reliable explanation of what was running when an action occurred. Record the
configured image reference with the exercise evidence. Some BOM references on
this branch use mutable tags, so do not describe them as immutable or attested
without separately resolving and pinning their registry digests.

The request path is:

`OpenClaw -> inference.local -> supervisor -> OpenShell gateway in the SAW VM -> provider`.

The real endpoint and credential remain gateway-side. Verify this boundary from
the effective provider configuration and sandbox environment before relying on
it as an operational control.

Proceed to xref:07-module-05-interact-with-agent.adoc[Module 5: Test Agent
Capabilities and Governance].
